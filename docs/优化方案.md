## 二、缓存调用链断裂（核心问题）

### 2.1 Celery 预热 100% 无效

```
Celery 每 10 分钟写入          页面实际读取           结论
──────────────────────         ──────────────         ────
banners:active                 banners:index          KEY 不一致
goods:recommended_top20        （无人读取）            死 key
nav:categories_with_counts     tt:navs:{is_nav}       KEY 不一致
stats:daily:{date}             （无人读取）            死 key
```

**影响：** `cache_warmup_homepage` 和 `daily_order_statistics` 两个 Celery 任务完全白费 CPU 和 Redis 内存。

### 2.2 热路径无缓存

| 路径 | 每次首页请求的查询 |
|------|-------------------|
| `get_index_floors()` — 首页楼层 + 商品 | 2 次 SQL（楼层分类 + 批量商品） |
| `parent_category_queryset` — 商品筛选页分类 | 1 次 SQL（每次列表页） |
| `child_category_queryset` — 商品筛选子分类 | 1 次 SQL（每次列表页） |

### 2.3 死代码

| 代码 | 位置 |
|------|------|
| `cache_query()` 工具函数 | `cache_utils.py:21` — 定义但无人调用 |
| `get_goods_categories()` + `categories:list` 缓存 | `public_service.py:109` — 有缓存但无人调用 |
| `get_hot_goods_list()` + `hot_goods:list:{limit}` 缓存 | `public_service.py:143` — 有缓存但无人调用 |
| 访问去重逻辑 3 处重复 | `models/visit.py` + `services/__init__.py` + `services/visit_service.py` |

## 三、推荐修复方案（按优先级）

### P0 — 修复 Celery 预热 key 对齐（高收益，低风险）

**改 1 个文件：`tasks.py`**

```python
# cache_warmup_homepage 任务中：
'banners:active'          → 'banners:index'
'goods:recommended_top20'  → 'hot_goods:list:10'
'nav:categories_with_counts' → 拆成 'tt:navs:1' + 'tt:navs:0'
```

**上下游影响：**
```
上游：Celery Beat 定时调度 → tasks.py（不受影响，只改 key 字符串）
下游：
  banners:index → baykeconfig.py:22 get_index_banners()
    → cache.get("banners:index") 命中 ✅
  hot_goods:list:10 → public_service.py:156
    → 但 get_hot_goods_list() 目前无人调用
    → 建议先不加，等确定页面渲染路径后再补
  tt:navs:1 / tt:navs:0 → baykeshop.py:263 navs()
    → cache.get("tt:navs:1") 命中 ✅
    → 注意：navs() 返回的是 QuerySet，Celery 写的是 list
    → 需要在 navs() 中兼容两种类型
```

**风险：低。** 只改 Celery 写的 key 名，不改变任何读取逻辑。最坏情况是 key 还是不匹配（比如 navs 的 QuerySet vs list 类型问题），但不会导致现有功能异常——只是预热仍然无效。

**验证清单：**
- [ ] `banners:index` 在 Celery 写后能被 `get_index_banners()` 命中
- [ ] `tt:navs:1` 在 Celery 写后能被 `{% navs %}` 命中（需处理类型兼容）
- [ ] 首页轮播图不因预热数据格式不同而报错

---

### P1 — 给 `get_index_floors()` 加缓存（高收益，中风险）

**改 1 个文件：`public_service.py`**

在 `get_index_floors()` 加入 Redis 缓存，TTL 10 分钟（与 Celery 预热频率一致）。

**上下游影响：**
```
上游调用方：
  views/public.py:12  BaykeShopIndexView.get_floors()
  → context['floors'] → index.html 渲染
  → 仅首页一个入口，调用面窄，改动安全

下游被调用：
  index.html → {% for floor in floors %}
  → floor.spu_list → 每个 SPU 附带了 spu_list 属性（Python list）
  → spu.html → {% score_avg spu %} → CommentService（已缓存）

缓存失效：
  - TTL 10 分钟后自动过期
  - Admin 修改分类/商品时主动失效：
    shop/admin.py 的 save_model/delete_model → 新增 delete("floors:index")
```

**需要注意的耦合点：**
- `spu_list` 是运行时动态设置在 category 对象上的属性，不是 model field
- 缓存时需要确保整个 `category_list` 可序列化（spu_list 是 list of model instances）
- 建议序列化方案：缓存时转为 JSON-safe dict，或使用 Django 的 `pickle` 序列化

**风险：中。** 缓存的是带动态属性 `spu_list` 的对象列表，序列化/反序列化需要验证。

### P2 — 清理死代码（低风险，改善可维护性）

以下代码可安全删除，经搜索确认无调用方：

| 文件 | 删除内容 | 确认方式 |
|------|---------|---------|
| `cache_utils.py:21-69` | `cache_query()` 函数 | 全项目 grep 无调用 |
| `public_service.py:109-140` | `get_goods_categories()` + `update_goods_categories_cache()` | 全项目 grep 无调用（admin 调用的是同名但不同的方法） |
| `public_service.py:143-183` | `get_hot_goods_list()` + `update_hot_goods_cache()` | 全项目 grep 无调用 |
| `tasks.py:186-205` | Celery 中预热 `goods:recommended_top20` 和 `nav:categories_with_counts` 的部分 | 对应 key 无人读 |

**注意：** `update_goods_categories_cache()` 目前在 `shop/admin.py:61/68` 被调用。如果删除此方法，admin 中的调用也需要同步移除，但 `tt:navs:*` 的清除逻辑需保留（可移到 admin 中直接写 `cache.delete`）。

---

### P3 — 首页楼层纳入 Celery 预热闭环

如果 P1（加缓存）和 P0（修复预热 key）都完成后，进一步把首页楼层也纳入 Celery 预热：

```
tasks.py cache_warmup_homepage 新增：
  floors = PublicService.get_index_floors()
  django_cache.set('floors:index', floors, timeout=600)
```

**上下游闭环：**
```
Celery(每10分钟) → 写 floors:index
       ↓
首页请求 → get_index_floors() → cache.get("floors:index") 命中
       ↓
Admin 改分类/商品 → cache.delete("floors:index") → 下次请求冷加载 → Celery 下次预热恢复
```

---

### P4 — 访问去重逻辑合并（低风险，消除重复）

`models/visit.py:24-26`、`services/__init__.py:37-38`、`services/visit_service.py:32-45` 三处有完全相同的 IP+日期+对象去重逻辑。建议统一到 `VisitService` 中。

## 四、不做修改的问题（有风险或收益过低）

| 问题 | 原因 |
|------|------|
| P1-5 Manager 默认 prefetch_related 过度 | 移除会波及 20+ 个调用点，每个都要补 prefetch，回归风险太大 |
| 会员 SerializerMethodField 查询 | 单用户页面，2 次额外查询可接受 |
| Redis 无降级方案 | 属于基础设施层面，需要运维配合，不是纯代码修改 |

## 五、实施顺序建议

```
第一轮（P0，1个文件）：Celery 预热 key 对齐
  → 立即可验证，无副作用

第二轮（P2，3个文件）：清理死代码
  → 减少代码量，降低后续修改的认知负担

第三轮（P1+P3，2个文件）：首页楼层缓存 + 纳入预热
  → 真正减少首页 DB 查询
  → 需在开发环境验证序列化正确性后再上线

第四轮（P4，3个文件）：去重逻辑合并
  → 代码质量改善
```
